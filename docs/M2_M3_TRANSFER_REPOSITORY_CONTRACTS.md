# Shared M2/M3 policy contracts (schema 1)

This source-only library owns policy and typed evidence, not Android persistence, HTTP, filesystem, APK installation, root operations, Vector IPC or release authorization. Consumers must use their own durable compare-and-set transactions and explicit user approval for privileged operations.

## Transfer contract

- `TransferRequest` binds an opaque Activity operation ID and opaque source/destination IDs to a safe ZIP/APK/archive filename, bounded size and optional expected SHA-256. The maximum library envelope is 1 GiB; consumers retain any tighter existing cap. Missing expected digest fails verified publication. No server URL, bearer token, signed redirect or raw ETag belongs in persisted Activity data.
- `TransferRecord` is a revision-checked state machine. Consumer storage must atomically admit a record and acquire at most two active transfer leases; every worker callback must use the current revision. A terminal Activity attempt is never retried in place: each new attempt uses a distinct Activity ID linked to the queue identity. The queue itself preserves staged progress, attempt counts and resume eligibility.
- Resume requires a strong representation validator, exact source identity, expected total, HTTP 206, identity encoding, exact range and body length. `ResumeProof` binds the observation to the original request and staged byte count. Rehash the entire staged file, not just appended bytes. On refusal, do not append; on restart, delete only the owned staging file and start at byte zero.
- The transport must validate each redirect and response before writing, hard-bound every received byte, and enforce actual free-space and cancellation. A consumer verifies module format with its existing inspector and SHA-256 from the completed file. `VerifiedTransfer` is unavailable without matching expected digest, positive length and format confirmation.
- A publication transition persists `PUBLISHING` before filesystem mutation. Under an exclusive destination lock inspect the target; never overwrite a conflicting file, and reject unsafe/non-regular targets. Use an atomic no-replace operation on the destination filesystem and then hash/read back the published bytes. A verified existing file may be reused only after exact observation and read-back. `TransferReceipt` cannot represent a staged partial. Process death during publication goes to `RECONCILIATION_REQUIRED` and requires destination read-back; never blindly replay a possibly successful rename.
- Automatic retry is bounded and only for transient reads. Retry wait is durable and respects the validated retry-after value. Cancellation before publication is final; after publication begins, reconcile rather than claim cancellation or success. An existing Activity attempt is not restarted after a terminal failure. The queue ID is stable across automatic retries and recoveries; each new attempt has a new app-owned Activity ID linked to the queue. Never reuse a terminal Activity record. `TransferBatchSummary` preserves mixed outcomes rather than marking a partial batch successful.

## Repository contract

- Require strict ASCII `owner/repository` and an exact numeric GitHub repository ID. Check returned canonical full name and ID on every refresh; do not silently adopt repository renames/transfers or a foreign identity.
- Filter draft releases and enforce saved stable/prerelease channel and module type. Reuse existing `ReleaseAssetIdentity`, `GitHubRunIdentity` and `Sha256Digest`. Require exact release asset URL, positive bounded asset identity and expected size. `ReleaseCandidate.revalidate` checks fresh metadata, not a stale cache entry.
- Actions requires explicit workflow-ID and branch allowlists, a successful completed same-repository push run, exact run attempt/commit, matching artifact ownership and non-expired artifact. Actions downloads are an outer archive, not a trusted root ZIP or APK. The consumer must separately inspect and select the actual nested payload and enforce its type and format. Revalidate the current run and artifact immediately before transfer.
- Use literal bounded include/exclude/preference rules; deterministic ranking is published time, preference, then stable identity. Duplicate candidate IDs are refused rather than resolved by arrival order. Cache state uses repository ID and consumer-owned generation; offline, expired or clock-regressed data is stale and may be displayed only with a stale label. No cache state is installation authority.
- JSON readers must enforce byte bounds before parsing, pagination and item count limits; `readPage` rejects empty, oversized and invalid UTF-8 bodies before parsing, and strict bounded scalar parsers reject oversized IDs and malformed digests. `RepositoryRedirectPolicy` is per-hop. Disable HTTP-client automatic redirects, never forward credentials on redirects, and never log signed redirect URLs or authorization headers. GitHub Actions outer archive provenance does not establish publisher or signer trust.

## Acceptance boundaries

N05A must run the existing and new JVM tests with the pinned Kotlin 2.2/JDK 21 hosted build. N05F may propagate only a qualified Shared source pin. MMRL `next` and MMRL-LSPosed `main` own persistence, network transfer, actual atomic publication, module inspection, Activity integration and physical-device gates. This document does not claim that either consumer has been integrated or accepted.
